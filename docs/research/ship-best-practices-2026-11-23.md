Use these criteria to audit the current [Ship skill](../../skills/ship-run/SKILL.md). Each criterion translates primary-source guidance into a check for Ship. Local anchors identify where to look. The evidence comes from published documentation and checkout inspection.

## Audit criteria

1. **Progressive disclosure.** Agent Skills loads metadata for discovery, `SKILL.md` on activation, and resources on demand. It recommends fewer than 5,000 instruction tokens, fewer than 500 lines, and references one level deep. [Agent Skills specification](https://agentskills.io/specification#progressive-disclosure)

   **Check** that an agent can select the lane, find each phase's completion rule, and reach the necessary command or reference from the entrypoint. Trace a normal run and one lane-specific path. Detailed material should load at its point of use, and gate rules should have one authoritative home. Ship's entrypoint is 262 lines in this checkout. [Ship entrypoint](../../skills/ship-run/SKILL.md) · [Context discipline](../../skills/ship-run/reference/context-discipline.md)

2. **Bounded workflow.** Agent Skills recommends checklists, validation loops, and validating an intermediate plan before destructive steps. Anthropic recommends observing tool results, pausing at blockers, and capping agent loops. [Agent Skills creator guidance](https://agentskills.io/skill-creation/best-practices#patterns-for-effective-instructions) · [Anthropic agent workflows](https://www.anthropic.com/research/building-effective-agents)

   **Check** that each phase advances on recorded evidence, each reviewer and CI wait has a finite budget, and resuming a wait preserves its deadline. Walk through a contested claim, a reviewer who never responds, and an exhausted retry. Each should reach the documented stop with the correct claim disposition. An unattended run should post the merge summary or hand back when blocked. [Ship stops](../../skills/ship-run/SKILL.md#the-stops) · [Mechanic waits](../../skills/ship-run/reference/mechanics.md#waits-past-540-s)

3. **External inputs and evidence.** OpenAI recommends keeping untrusted text out of privileged instructions and constraining its downstream use with structured fields. GitHub identifies issue titles and PR bodies as untrusted script inputs. [OpenAI agent safety](https://developers.openai.com/api/docs/guides/agent-builder-safety#use-structured-outputs-to-constrain-data-flow) · [GitHub script injection guidance](https://docs.github.com/en/actions/concepts/security/script-injections)

   **Check** that issue and PR text, reviewer output, and logs enter as data. A scope-changing comment needs the host-backed authority required by Ship and a recorded author, timestamp, and source. Exercise `writer: false` and `writer: null`. For external behavior claims, require current official docs and an authorized probe of the relevant environment where the claim depends on live behavior. Log the target and observed result, and leave unavailable evidence visible. A result that disproves the brief should trigger `mis-specified` before implementation. [Spec precedence and external claims](../../skills/ship-run/reference/implement.md)

4. **Exact commit and merge authority.** GitHub's synchronous merge takes an expected `sha` and rejects a mismatch. It does not support merge queues. The asynchronous API also accepts `sha`, supports queues, and exposes a separate result. Azure DevOps documents `lastMergeSourceCommit` and a separate policy-bypass option. Its REST reference leaves stale completion rejection unspecified. [GitHub synchronous merge](https://docs.github.com/en/rest/pulls/pulls#merge-a-pull-request) · [GitHub asynchronous merge](https://docs.github.com/en/rest/pulls/pulls#merge-a-pull-request-asynchronously) · [Azure DevOps PR update](https://learn.microsoft.com/en-us/rest/api/azure/devops/git/pull-requests/update?view=azure-devops-rest-7.1)

   **Check** that the summary, local gate, and merge admission bind the full reviewed head SHA and the intended PR and base. Require explicit human approval or a clean gate under the trusted profile's opt-in. Keep host enforcement and Ship admission distinct, preserve raw holds and any explicit waiver, and exercise a push between the final read and merge. Verify that a host-policy refusal cannot lead to an implicit bypass. Also exercise a target-branch advance and revalidate affected evidence. Ship's Azure adapter sends the recorded SHA. A host fake can verify the payload, while stale-write rejection needs host-side evidence on a fixture repo. [Ship merge gate](../../skills/ship-run/reference/merge-gate.md#attended-post-then-wait) · [Azure adapter](../../skills/ship-run/scripts/host/ado.d/threads-and-lists.sh#L57)

5. **Review and CI freshness.** GitHub can dismiss stale approvals or require approval of the latest reviewable push. Rulesets layer with branch protection. Required checks use the current applicable commit, which may be the test merge commit. GitHub Actions workflows that supply required merge-queue checks need the `merge_group` trigger. Azure Repos can require approval on the latest iteration or reset votes on pushes. Its build policy can expire validation when the target advances. [GitHub protected branches](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches) · [GitHub rulesets](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/about-rulesets#about-rule-layering) · [GitHub required checks](https://docs.github.com/en/pull-requests/how-tos/merge-and-close-pull-requests/troubleshooting-required-status-checks) · [Azure Repos branch policies](https://learn.microsoft.com/en-us/azure/devops/repos/git/branch-policies?view=azure-devops)

   **Check** that a landed review round records reviewer identity, trigger, commit or iteration, and finding dispositions. A timestamp-qualified round can supply findings, but final-head coverage needs its own evidence. Compare configured CI legs with effective host policy and preserve which commit, run attempt, and check source supplied each verdict. Test missing, pending, stale, and wrong-source results plus a rerun on the same SHA after a PR edit. Treat unreadable protection as `unknown` in the summary and keep that report distinct from the merge admission decision. [Ship review rounds](../../skills/ship-run/reference/review-loop.md) · [Ship merge evidence](../../skills/ship-run/reference/merge-gate.md#the-summary)

6. **Retry and recovery.** AWS recommends bounded retries at one layer, backoff with jitter, and stable request identifiers where supported. A lost response can follow a successful write. Step Functions redrive illustrates resuming at the failed step with completed results preserved. GitHub distinguishes queued from merged. [AWS retry guidance](https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/) · [AWS idempotency guidance](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/) · [Step Functions redrive](https://docs.aws.amazon.com/step-functions/latest/dg/redrive-executions.html) · [GitHub merge result](https://docs.github.com/en/rest/pulls/pulls#get-the-result-of-an-asynchronous-merge)

   **Check** that transient failures and rate limits have a bounded retry path. For an ambiguous write, reconcile durable host state before replay. Simulate a lost response after PR creation, a comment, and merge. Prove there is one intended effect, or a named stop when identity is ambiguous. Resume partial completion from the Run file and host read-back. A confirmed merge and any unfinished tracker update or authorized cleanup should be reported independently. [Mechanic outcomes](../../skills/ship-run/reference/mechanics.md#flags-exit-codes-and-failed-writes) · [Ship merge mechanic](../../skills/ship-run/scripts/merge.sh)
