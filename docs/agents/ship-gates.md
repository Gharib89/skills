# Ship profile: gate notes

What each gate in the ship profile's `## Local gate` runs and why. The profile ([ship.md](ship.md)) keeps the lines a run reads at its start; this file is the reference for a run that has a gate to read about. Vocabulary: [GLOSSARY.md](../../GLOSSARY.md).

`tests` runs `tests/run.sh`, which runs every `tests/*.test.sh` concurrently (`SHIP_TEST_JOBS` bounds the workers, default the CPU count) and reports them in file order. None reaches a host: `tests/host-stub.sh` puts a `gh` and an `az` that record the call and fail in front of PATH, one host log per file, and a file whose run leaves entries in its log fails by name. Each test file's header says what its subject is and how it is driven; a new test carries that description there, and this section gains a line only for a new kind:

- a pure function, sourced and asserted on strings (`body-section`, `triage-label` over a fixture checkout);
- a gate script, run once per fixture, asserting its exit code and stdout (`contract-gate`);
- a mechanic's usage guard, invoked malformed (`manage-issue-usage`);
- an order of calls, over stub functions (`create-verify`);
- the request a function sends, over a fake `gh` on PATH (`api-retry`);
- a mechanic driven end to end over scratch directories (`run-file`, `update-skills-plan`);
- a mechanic over the Host fake, `SHIP_HOST_ADAPTER` at `tests/host-fake.sh` (`reviewer-run`, `host-contract`);
- a mechanic over the real GitHub adapter and a fake `gh` answering per endpoint (`request-review-readback`, `gh-threads-proxy`), or over a fake `herdr` (`drive-session`);
- one adapter function, its transport redefined as fixtures (`ado-reviews-substantive`, `gh-run-denials`);
- a shipped template or script over stub tools in a throwaway checkout (`harness-check`, `setup-skills-bootstrap`, `explainer-video`);
- a shipped file's text, read as files (`template-pins`, `reviewer-refresh`);
- a shipped page's script, run headless under `node` over JSON fixtures, its reads recorded through proxies (`grill-with-artifact`).

The catalog's entry trial, `scripts/catalog-trial.sh`, is no gate here: it installs real tools globally, so it runs in a cloud session before an entry merges. A behavioural claim about one of these subjects earns a case here, where it survives the run that made it, instead of a scratchpad probe that does not. A `host_*` function's live call stays its host's verification's job, `github-mechanics` or `ado-mechanics`: a test that reaches a host is that verification, not this gate.

`prose-budget` holds the shape of the skills' own documents, the one gate here whose subject is prose rather than a script: `skills/*/SKILL.md` at most 3500 words, and every `skills/*/reference/*.md` over 100 lines opening with a `## Contents` heading inside its first 15 lines whose list matches the file's `## ` headings, each heading listed and each entry naming a heading that exists. A run reads `SKILL.md` whole at load and re-reads it after a compaction, so a file that outgrows the budget spends that read on reference material and reaches phase 0 late; the `## Contents` list is what makes a long reference file answerable without reading it through, and a list that drifted from the file sends that reader to a heading that is not there, which is worse than no list. `scripts/prose-budget-check.sh` is the whole rule, a script rather than a function in the gate so `tests/prose-budget.test.sh` can drive it against fixture trees, the way `derived-copies` calls `scripts/profile-schema-check.sh`. A `## ` inside a fence is an example: it needs no entry, and no entry may name it. It also holds this profile's own `## Local gate` section to 11000 bytes, because every run reads the profile at its start.

`version-lines` refuses a diff that changes a `metadata.version` line under `skills/`, which `## Versioning and changelog` below hands to the release run on main. `scripts/version-line-check.sh` is the whole rule: it compares the merge base with the working tree, so an uncommitted bump is caught alongside a committed one, and it needs a *removed* version line, because a new skill arrives carrying its first and a file can gain a metadata block it did not have. `metadata.profile-schema` is exempt, and so is the renumber `M.m.p` to exactly `0.M.p` in the diff that flips the skill's `allow_zero_version`, which happens once per skill ([ADR 0005](../adr/0005-skills-stay-0x-until-public-release.md)).

`stray-files` refuses a tracked path outside the top-level entries this repo owns, the allowlist being `dirs` and `files` in `scripts/stray-file-check.sh`, stated once more in that file's header. It reads the index rather than the working tree, so scratch a run leaves behind is not a finding and a file a `git add -A` swept in is.

`self-contained` refuses a skill document under `skills/` that points at material a derived copy does not carry: any URL into this repo but its root and issue tracker, in any case, and, outside a code span or a fenced block, a `PR #N` or `issue #N` in any case, or a relative link leaving `skills/<name>/`; `CHANGELOG.md` is exempt. `scripts/self-contained-check.sh` is the whole rule; the coding standards' self-contained bullet is wider than the grep.

`contract` holds a new mechanic of any skill but setup-harness, each directory run on its own, to the malformed-invocation contract `## Public surface` names: no `${N:?}` or `${N?}` expansion under the mechanics, and a bare invocation of one that requires an argument answering with a single JSON error object and exit 2. A third check traverses the whole `skills/` tree rather than the mechanics alone, for the Bash 4 constructs a consumer machine's Bash 3.2 lacks. A fourth invokes every mechanic that takes a positional with one, two and three `--x` arguments and holds each answer to that mechanic's own usage line and exit 2, because a flag typed where an id belongs is a malformed invocation, not an id. A fifth holds every mechanic, none exempted, to answering `--help`, on stdout, with its own usage line then its header's `stdout:` block, exit 0 and nothing on stderr: that is where a run reads a mechanic's flags and output fields, so an answer it cannot trust is worse than none. The gate reaches no host while the contract holds, because every usage guard fires before its mechanic loads the adapter: an unguarded mechanic is what makes check 4 reach one, and that call is the finding. Check 5 is where placement stops being a convention: it runs each mechanic from a directory where no origin remote resolves, so a guard sitting after `ship_load_host` answers `--help` with the adapter's tooling error and fails, while a mechanic that guards first answers its usage line from anywhere. It also holds that answer to the same string the mechanic's own guards print, because the two are separate paths and a second copy going stale is what this contract replaced; `base-fresh` and `select` are the only two that comparison skips, their guards answering a bad call with a takes-no-arguments line rather than a usage one. A sixth holds `SHIP_HOST_ADAPTER`, which swaps the host adapter for the test suite's Host fake, to its one reader, `ship_load_host` in `_lib.sh`: any other mention under `skills/`, prose included, is a mechanic that can be pointed off its host. A seventh holds every setup-harness catalog entry to the entry format `catalog/README.md` fixes (`## Signals` first, roles from the fixed set, every tool block carrying every label, a `Library:` signal on every stack and on no file kind), and refuses `Rung: turn` in a file-kind entry, any rung but `full` for `browser` and `public API`, a `language server` tool with a rung, a hook or no `Local-only:` reason, and `Hook: None.` on any other tool. An eighth holds the two harness-profile lines setup-skills reads without a schema check, in its harness detection and in its cloud bootstrap template, `Location:` under `## Check entry point` and `Setup:` under `## Cloud`, present in the profile template, since renaming either is a major of both skills. A ninth holds `metadata.harness-schema` in setup-harness' `SKILL.md`, the `Schema:` line in its profile template and the `schema=` literal in `harness-profile-check.sh` equal, and requires a `## Schema <n>` entry for that number in `harness-schema.md`, the places its bump rule moves together, as `derived-copies` holds the ship profile's number, because one moved alone ships a template its own checker refuses; a place it cannot read is tooling, exit 2. The last three run only when the skills tree carries setup-harness. Checks 10 to 15 are listed in `docs/contributing/standards/gates.md`.

`derived-copies` is the drift gate. Its set is the lock's `source: "."` entries. It fails when `.claude/skills/<name>/` differs from `skills/<name>/` for one of them (making the refresh below non-optional), and when a `skills/<name>/`, a `.release/<name>.toml`, the release workflow's `SKILLS` list, its release-commit conditions or `.gitattributes`' `linguist-generated` lines disagree with the set. It also holds the profile schema number consistent across the three files the bump rule in `docs/contributing/standards/release.md` moves together, the `Schema:` line in `skills/setup-skills/ship-profile.md`, `metadata.profile-schema` in `skills/ship/SKILL.md`, and ship's `## Schema <n>` entry in `skills/setup-skills/profile-schema.md`, failing with one message naming all three. That is the same drift a level up: a ship moving to a new schema while the template stays at the old one has every profile drafted from that template refused by the next run, every gate green. It runs `scripts/pin-check.sh` too, which holds every pinned ref a skill states, a `metadata.composes` entry or a printed `npx skills add <owner>/<repo>#<sha>` line, at a line's start or opening a code span, to the `ref` `skills-lock.json` records for that skill: the lock is what this repo tested, so a pin that moved without a refresh, or a refresh that left a pin behind, ships consumers a commit nobody ran.

The two CI legs of this profile's `## CI` have their own notes below.

`check-full` (`.github/workflows/check-full.yml`) runs on `pull_request` opened, synchronize and reopened (the default types), is not path-filtered, installs the tools `.claude/hooks/cloud-setup.sh` names (its `STEPS` block is the one place their versions live), and runs `scripts/check.sh full` on the head: the local gate less `secrets` and `version-lines`. A red run is a failing test or check on the head, to fix on the branch; its log carries `check.sh`'s JSON line and each failing check's tail. Any nonzero exit fails it, 2 (a tool unavailable) and 3 (over budget) included.

`bump-guard` runs on `pull_request` opened, edited, synchronize, labeled and unlabeled, is not path-filtered, and reports on every PR, so a run always has a check to await. Its subject is the PR title, because the release run on main grades the bump from the squash subject; it also checks the body against the PR template's `##` headings, and holds `## Change outline` to the Shape bullet of [release.md](../contributing/standards/release.md): a `diff` fence or a `Shape: none, mechanical (` line, the first `diff` fence at most 15 lines (a hard cap here, where ship's `pr-body.md` says "preferably"), each root line in it carrying a file path, and each call node one level under a root a word of that root's file. A red leg here is a title to fix with `update-pr-title`, or, when it names a missing body heading or a `change outline` rule, a section to fix with `update-pr-body`. It reads the branch's commit messages too, because a `BREAKING CHANGE:` footer in one of them reaches the release run through the squash body, and it reads the description for the same footer, so neither text grades a major bump the guard has not seen. Every skill is 0.x until its public release ([ADR 0005](../adr/0005-skills-stay-0x-until-public-release.md)), so a breaking change is titled `feat(<skill>):`, which cuts the same minor a `!` would, and states its break in plain words in the commit body and under `## Special things to note`; the title, every commit and the description stay free of `!` and of the footer, and the leg stays green. The one red run cannot clear is the `major` label, which only the maintainer applies: on the PR that releases a skill at 1.0, and on every breaking change after, the title keeps its `!`, the leg stays red, and the run asks for the label at the merge gate.
